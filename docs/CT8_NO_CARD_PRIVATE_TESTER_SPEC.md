## Evidence and decision

The owner-only Render Free measurement completed two *fixed synthetic* CT7 scenarios: catalogue full-response digest matched in 5.637 s from the owner client (server 4.686 s), hours-clause matched in 4.509 s (server 4.122 s). The cgroup peaks were 118,099,968 and 118,382,592 bytes respectively, against a 536,870,912-byte limit. Those fixtures are only one catalogue trial/occurrence/layer (2,378-byte input), and two hours components/one layer (2,934-byte input). These results do not establish a safe capacity for other inputs, concurrent callers, or full CT6 legal maxima. An initial 401 was resolved before both successful runs. The service was suspended after a fail-closed redeploy; no invited-user URL exists.

Cloudflare Zero Trust Access checkout requested a payment method and consent to possible charges. The owner does not want that arrangement. Render Free cannot provide service-level inbound IP rules on the current workspace plan; Render's documentation restricts them to Scale/Enterprise. Neither a publicly visible static React bundle nor secrecy of a URL counts as authentication.

**Recommended candidate (revised after Claude review):** a new, *separately versioned* CT8 invited pilot using a dedicated Cloudflare Free Worker on `asif-rox.workers.dev` as the browser origin. The **Worker performs GitHub OAuth and owns the browser session**; the existing Render Free instance only verifies a short-lived signed Worker assertion and runs Python calculations. GitHub identity is a deliberate pilot limitation: every tester must have a GitHub account, and the owner must approve their **numeric GitHub account IDs**, not usernames or email strings. GitHub OAuth App registration and Free Worker availability must be confirmed in the owner's accounts before implementation is treated as deployable. If testers cannot use GitHub accounts, this candidate requires a separately reviewed identity choice; do not substitute shared passwords or an unauthenticated endpoint.

| Boundary | Proposed control |
| --- | --- |
| Worker/UI | A new dedicated hostname under the existing `asif-rox.workers.dev` account; serves only the reviewed CT8 pilot build. It does not reuse or alter EdInsured Live or another lab. Assets may be public only if they contain no tester data or secrets. `run_worker_first=true` covers **all** paths; the Worker fixes allowed methods/paths, rejects unknown paths and query shapes before fallback to SPA, applies available location-local edge rate controls, and forwards only accepted API routes to Render. No CORS preflight or cross-origin browser API call. |
| OAuth | **Worker-only** authorization-code exchange with GitHub using unpredictable browser-bound `state`, PKCE S256, a fixed HTTPS callback URL, bounded outbound fetches and minimal/no requested scopes. Short-lived pre-login state cookie must be `SameSite=Lax` for GitHub's cross-site redirect. Clear it after callback and consume the one-use GitHub code. Query values never establish identity. Fetch GitHub `/user`, accept only an explicitly allowlisted numeric ID, then discard the GitHub token. Suppress callback query/code from application logging, immediately redirect with `Referrer-Policy: no-referrer`, and fail closed on GitHub/network errors. |
| Session | Worker issues a signed, short-TTL (provisional 15 minutes) cookie containing numeric ID, issue/expiry and epoch; no credential in React storage or URL. Cookie is `__Host-CT8PilotSession; Secure; HttpOnly; SameSite=Lax; Path=/`, with no Domain, and duplicates are rejected. Check the current allowlist on **every** request; epoch/key rotation revokes all sessions. Logout clears the browser cookie, but a stolen cookie remains usable until its expiry unless the epoch is rotated. Require exact Origin plus session-bound CSRF header for mutating API calls; guard login CSRF with state/PKCE. `workers.dev` is in the Public Suffix List; sibling Workers under `asif-rox.workers.dev` are same-site, so SameSite alone is not a CSRF defense. Include the existing sibling-worker risk in the threat model. |
| Origin | Worker first fetches the current Render process readiness token, then signs a **per-request** assertion covering version, explicit key ID, method, exact path, Render Host, public Host, numeric ID, body SHA-256, timestamp, unpredictable nonce and that boot token. Python checks the boot token, exact Host, signature, independent ID allowlist and single-use nonce **before reading the body**. A restart generates a different boot token and invalidates captured old assertions. After a bounded streamed read, Python recomputes SHA-256 and compares with the signed digest. The Worker strips incoming browser proof/identity/forwarded headers. Body size and rate controls at both boundaries precede model validation. This requires exactly one API worker and one instance; real-host cold-start and replay tests remain required. |
| Computation | Separate opt-in pilot factory; one Render instance and one Uvicorn worker; isolated Python child with fixed deadline and one per-process calculation slot. **The existing 128 MiB CT8 executor guard is not a safe Free-tier response budget**: define a lower pilot-only serialized/response ceiling from actual whole-process measurement (evaluate 16–32 MiB rather than adopting either value without data). Bound the child result before parent deserialization where feasible. Preserve frozen CT0–CT7 calculators, responses, deterministic hashes and reconciliation. React only presents requests and authoritative backend results. CT6 `/api/v1/*` is absent. |
| Deployment | Secrets only in provider environment; no credentials, allowlist IDs, real inputs or tokens in code, frontend, build artifact, logs or review ZIP. Auto-Deploy Off. No new domain, Zero Trust payment, or paid Render instance assumed. |

### What must be measured before choosing an invited envelope

The 1-trial/1-occurrence and 2-component fixtures prove a *floor for those exact examples*, not a limit for an editable UI. Implement seven explicit Python pilot limits already present in `PilotLimits` (`max_body_bytes`, `max_trials`, `max_occurrences`, `max_layers`, `max_hours_components`, `max_requests_per_minute`, `allow_full_detail`), then measure each enabled UI route, guided scenario and boundary input on the actual 512 MiB/0.1 CPU host, including two competing requests. Set exact numerical limits **after** the measurements and independent review. A route/scenario that cannot run within the measured envelope stays disabled and clearly labelled in the pilot UI; no silent truncation or math change. Conservative provisional stop rules remain peak >384 MiB, a warm request >30 s, restart/OOM, missing cgroup peak, wrong CT7 digest, extra worker/instance, authentication bypass, or unexpected charge. The final 512 MiB free-instance capacity decision stays open.

4. Perform rollback: revoke access first, disable pilot flag/suspend service, confirm direct Render and Worker routes cannot calculate, and verify no automatic redeploy. Rotate the measurement secret left from the earlier exercise and remove unused measurement variables. Preserve logs of outcome codes and resource counters only; retain only numeric IDs needed for the active allowlist, delete them when the pilot ends, and state a finite log-retention period. No raw OAuth code/token or request body is logged.
5. Present the final exact numerical envelope, named tester identities/count (privately), reviewed commit/ZIP digest, browser test evidence, cost plan and rollback result for owner acceptance **before** inviting anyone. Full public CT6 workload remains a separate decision.

## Exact questions for independent Claude review

1. Does GitHub's current OAuth App web flow support this exact Worker state + PKCE S256 design with no requested scopes and a fixed `workers.dev` callback? Can numeric `/user.id` be verified without email scope, and how are code/token leakage, callback replay, GitHub downtime and login CSRF handled?
2. Does the signed method/path/host/body-digest/timestamp/nonce assertion genuinely protect direct `onrender.com` (including spoofed Host, forwarded headers, copied cookie and replay across a restart)? Can Python verify before body read while still detecting a different actual streamed body? Is independent Python ID revocation immediate enough?
3. Do assets, API/auth route ordering, `run_worker_first`, caching and redirects expose a path around login or allow scripts/secrets into the build? Does the frontend work same-origin without CORS, and is an unauthenticated UI shell acceptable for this pilot?
4. Are short signed Worker sessions, `__Host-`/Lax cookies, duplicate-cookie rejection, epoch revocation, exact Origin/CSRF and sibling-Worker threats handled correctly? Is logout behavior honestly described, including stolen-cookie reuse until TTL/epoch rotation?
5. Can repeated unauthenticated requests or direct-origin denials exhaust a 0.1-CPU/512 MiB host despite Worker rejection and location-local rate limits? Which measurable pre-auth admission and monitoring controls must be added before invitations? Would this design remain no-card on the owner's actual Cloudflare and GitHub accounts?
6. Do pilot limits reject excessive JSON, nested/streaming bodies, large responses and concurrent calls **before** costly model validation or spawning a second child? Does a lower pilot-only result ceiling hold under full response serialization and 512 MiB whole-process memory? Which editable UI scenarios were actually measured, and must some routes be hidden until they pass?
7. Are the CT0–CT7 actuarial results, hashes, reconciling evidence and learning controls preserved under this new auth transport? Specify negative tests for CT6 endpoint absence and direct origin access.
8. Is the proposed review → implementation → real-host measurement → physical-browser acceptance → rollback → explicit invitation order adequate? Name any launch blocker or less complex no-card identity option that meets the same security boundary.
