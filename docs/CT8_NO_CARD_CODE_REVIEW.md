## Actual changes

- Separate opt-in Python factory `create_nocard_app`: refuses to start unless the old pilot and measurement modes are false, requires exact Render/Worker hosts, numeric GitHub-ID allowlist, a high-entropy assertion key, explicit `PilotLimits`, deadline <=30 seconds, and a provisional <=16 MiB result cap. Frozen CT6 `api:app` and actuarial engines are untouched.
- Every pilot API route verifies current/previous-key HMAC over method, path, both hosts, numeric ID, SHA-256, timestamp and 24-byte nonce before reading the request body. The one-worker nonce cache rejects repeat use in that process; actual streamed bytes are hashed and compared after the body cap. Direct requests without proof, wrong IDs, or copied cookies are rejected. Nonce cache is lost on process restart; an assertion captured in transit could be replayed in the remaining 15-second skew after a restart. This is an **open security review item** before invitations.
- Dedicated Worker handles state + PKCE GitHub OAuth with no requested scope; accepts only allowlisted numeric `/user.id` and discards the access token, issues a 15-minute signed `__Host-` Lax cookie, checks cookie duplicates/allowlist/epoch, and requires an exact Origin plus session CSRF token on POST. The Worker strips the browser's cookies and all incoming identity/proof headers before signing and forwarding bounded requests. Assets are public but audited; `run_worker_first=true` is required. Cloudflare callback provider logs and GitHub token-grant revocation remain for live-account review.
- The existing executor accepts a narrower optional per-run serialized result ceiling, passed to the child and pipe; default stays 128 MiB for existing modes. The child still constructs/serializes its result before rejecting an oversized pickle, so **no memory-capacity conclusion** follows from 16 MiB alone. The UI adds a GitHub sign-in link and fetches a session-bound CSRF token before pilot POSTs. Default CT7/CT6 build stays separate.

## Review questions requiring disposition before any external host change

1. Does a 15-second signed assertion plus one-process nonce cache create a relevant cross-restart replay gap? If so, require a start-specific challenge or atomic shared nonce store; test it against a restarted process with a captured assertion before launch.
2. Is the Worker OAuth code exchange correct for real GitHub OAuth Apps (client ID/secret formats, no-scope identity, PKCE, state cookie, callback query, rejected redirect, suppressed code/token logs)? Does the login-state cookie require stronger single-use protection? Does logout's stolen-cookie limitation require server-side revocation?
3. Do Lax `__Host-` cookies, exact Origin, CSRF header and duplicate-cookie rejection close attacks from sibling `asif-rox.workers.dev` Workers? Test actual browser behavior across the GitHub callback and sibling origins.
4. Can malformed, missing or chunked Content-Length and large streamed bodies reach expensive work at either boundary? Verify that Worker stream cancellation and Python early HMAC checks work against direct origin, host/header spoofing, two concurrent calls and a disconnected client.
5. Is the Python child pickle/result cap useful for 512 MiB sizing given pre-serialization peaks? Which *measured* pilot envelope and result cap fit both catalogue and hours routes on the 0.1 CPU Render Free instance? Hide unmeasured guided/compare requests and enforce exactly one worker/instance.
6. Are GitHub OAuth App, Worker rate limiting binding, static assets and preview/production hostname configuration actually no-card in the owner's accounts? Does any provider log a callback URL containing `code`? What stops a public Worker Free quota exhaustion from making the pilot unavailable?
7. Are frozen CT0–CT7 computation, full-response identities, error categories, UI learning controls and CT6 endpoint absence preserved? Are Python assertion verifier and Worker signer canonicalization unambiguous and interoperable with proxies and real HTTP headers?
