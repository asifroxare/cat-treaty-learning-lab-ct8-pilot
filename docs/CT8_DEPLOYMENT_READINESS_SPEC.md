## B. Hosting decision and threat model

**Proposed topology:** immutable static Vite frontend at a Treaty Lab HTTPS host and versioned FastAPI service behind a separate HTTPS API origin. Exact hostnames and provider remain decisions for the owner. Build `VITE_CT6_API_BASE_URL` with the exact public API origin; it is public configuration, never a secret. Use an explicit exact-origin `CT6_CORS_ORIGINS` list and credentials disabled. Retain separate routing, branding and artifacts from the Pricing Lab. A same-origin `/api/*` reverse proxy is a viable alternative requiring a reviewed frontend configuration and ingress design; choose one topology before implementation.

**Security boundary:** CORS only governs compliant browsers. Neither CORS nor a same-origin proxy prevents direct non-browser API calls. Public API abuse must be controlled at the ingress and workload level. Ingress enforces TLS, exact trusted hosts, narrowly scoped forwarded-header trust, body-size limit before buffering when supported, request-rate and global active-computation caps, and independently measured CPU/memory ceilings. Verify whether the deployed ingress actually rejects oversized streaming bodies before application buffering. Avoid trusting client-supplied IP headers for limits.

Backend currently has a 25 MiB request limit, 10,000-trial and 100,000-occurrence maxima, a 25,000-row full-detail cap and synchronous Python computation. It has no application computation deadline. Benchmark max-sized legal requests, including combined worst-case dimensions, and representative traffic; record wall time, CPU, peak RSS, response size, concurrency and restart behavior. Set actual worker count, queue size, global active-work cap, per-client and per-route rate thresholds, memory/CPU limits, ingress/body timeouts and a clean computation deadline from the measurements. A gateway timeout alone must never be described as cancellation: establish a proven worker/process termination or equivalent safe bound so abandoned requests cannot keep occupying compute indefinitely. Rejected requests never enter computation; an accepted run either returns the complete authoritative result or a reviewed structured failure, never partial results. If that requires altering CT6 success/error behavior, use the frozen-contract revision process. The owner must explicitly decide whether public maximums may be lower than frozen CT6 limits; no silent reduction.

## C. Runtime and release configuration

Production API: `CT6_HOST=0.0.0.0`; host-provided `PORT`; `CT6_LOG_LEVEL=info` or stricter; exact production-only `CT6_CORS_ORIGINS`; `CT6_CORS_ALLOW_CREDENTIALS=false`. Existing API allows GET/POST/OPTIONS and `Content-Type`, `X-Request-ID`; preserve the required preflight behavior unless a CT6 contract revision is approved. Validate trusted hosts, real proxy IPs and host-header spoofing. Document whether `/docs`, `/redoc`, `/openapi.json` are public or internal; retain a frozen OpenAPI artifact for digest verification. Review the placeholder problem type domain without changing the frozen wire contract casually.

TLS redirect, certificate renewal and appropriate HSTS, CSP, `nosniff`, referrer and frame policies need real-browser verification against built assets. Confirm whether the actual Vite output needs CSP allowances; avoid broad inline/eval permissions. Static `index.html` must revalidate; fingerprinted assets are immutable and retained across releases for open old tabs. Missing asset URLs return 404 rather than SPA HTML. Do not cache API POSTs in a shared cache. No `.env`, credentials, `.git`, `.venv`, `node_modules`, source maps or test artifacts in production packages. Log only route, status, request ID, duration, coarse size and release identifier, without treaty payloads or response bodies. Choose retention, privacy notice and incident owner before launch.

Build frontend once per target API origin. Record source commit, CT7 input digest, frontend/backend artifact digests, dependency lock resolution, runtime versions, OpenAPI digest and check results. Promote the same reviewed candidate to staging and production, with only documented environment differences. Test Windows reproduction on a path containing spaces. Resolve the Node `[DEP0190]` warning by a narrow reviewed change or explicitly accept its bounded operational impact. No generated business formulas in React.

## D. Golden contract and precedence evidence

Before running staging comparisons, freeze named golden fixtures and an exhaustive list of transport fields permitted to vary (such as request ID). Any additional normalization requires a documented finding; never normalize a business field to force a pass. Confirm canonical business hashes exclude nondeterministic transport timing/IDs. Golden fixtures compare authoritative values and learning facts, deterministic metadata/hashes, reconciliations, warnings, exclusion reasons, independently all three settlement fields, and neutral wording. Include catalogue and hours-clause workflows, legal election methods and rejected candidates, zero-capacity and other CT0–CT7 boundaries, and exact maximum/one-over request limits where practically constructible. Freeze/hash the OpenAPI and capabilities payloads using documented canonicalization.

Write a middleware/ingress precedence matrix before changes: malformed and oversized bodies, wrong media type, version conflict, schema/domain/contract errors, disallowed origin, host rejection and rate-limit rejection, individually and in meaningful combinations. Some ingress rejections cannot use existing CT6 problem JSON; explicitly document the external response and where CT6 precedence begins. Test simultaneous active controls, not isolated toggles. Rate limiting rejects before compute; accepted results remain byte-identical to baseline business evidence. A new timeout response, if introduced, requires explicit wire-contract review and tests for no partial result.

## E. Physical browser and real-service E2E

On staging production assets and the real CT6 service over HTTPS, exercise Explore Treaty, Hours-Clause Lab, Guided Lab and Audit Trail; seven experiments, freshness transitions, exclusion and election evidence, structured errors, direct SPA route refresh, CORS preflight/denial, offline/recovery, size/rate/concurrency limits, and performance. Use current Edge, Chrome and Firefox on desktop plus responsive/mobile widths, keyboard-only operation, 200% zoom and NVDA smoke. Include Safari/WebKit with VoiceOver when feasible; if unavailable, record the coverage gap and assess launch impact explicitly. Test reduced motion, forced colors and high contrast, especially warnings and exclusions. Record device/browser/version, viewport, case, result, screenshot/video and request ID. No material accessibility blocker, console error, misleading number or invented conclusion remains.

Automate neutrality checks on API response learning text as an additional gate while preserving the existing frontend content lint and manual semantic review. Test open release N tab after release N+1, old fingerprinted asset availability, cache behavior at actual CDN edge, and graceful handling of API version mismatch. Never substitute mocks for production-like E2E. Thresholds for p95 latency and concurrent throughput must be chosen from benchmarks before declaring a pass.

## F. Monitoring, rollback and acceptance

Probe `/health/live` and `/health/ready`; run non-sensitive fixed catalogue and hours-clause synthetic checks against expected hashes. Monitor availability, 5xx/error codes, p95/p99 latency, rejection counts, queue/concurrency saturation, RSS, CPU, restarts, TLS expiry and static asset failures. Define numeric alert thresholds, channel, on-call owner, retention and incident steps before public launch. Periodically review dependency/security advisories.

Keep the last compatible frontend and API pair with digests and deployment settings. Roll both back together, revalidate or purge cached `index.html` at the CDN, and retain old fingerprinted assets for open tabs. Verify health, capabilities/OpenAPI, fixed golden hashes, browser smoke and synthetic monitoring after rollback. Stage and record an actual rollback drill with operator, trigger, duration and evidence. An optional phased rollout can reduce risk but does not replace the drill.

**Launch gates:** topology/host/cost decision; signed threat and environment matrix; measured workload and enforced resource controls with proven compute termination; frozen error-precedence matrix; golden fixture and fixed-normalization evidence; reviewed immutable build; backend/frontend/live API checks; physical browser/accessibility matrix; real-service E2E with security controls simultaneously active; numeric monitoring and incident ownership; compatible rollback drill; independent security/domain-integrity audit; owner sign-off on exact artifacts and public deployment. Failure at any gate blocks deployment. The specification approval authorizes planning only; implementation and public deployment are separate decisions.

Claude's review is incorporated as follows: resource-exhaustion and cancellation, rate limiting, numeric monitoring, error precedence, comprehensive golden fields, browser/CSP evidence and open operational ownership are launch gates.
